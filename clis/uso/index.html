    Marco común de los CLIs

    Todos los CLIs de la suite comparten un mismo marco (iec_core.cli), de modo que el contrato es idéntico app por app: los mismos flags de salida, la misma disciplina de streams, los mismos exit codes y el mismo descubrimiento por introspección. Esta página documenta ese marco común una sola vez; cada página de CLI enlaza aquí y describe únicamente sus flags propios.

    Para quién es

    Pensado para uso headless (sin GUI) por ingenieros avanzados y, sobre todo, para consumo por agentes y LLMs. La salida es estable y parseable, los errores van siempre a stderr y el exit code permite ramificar sin leer prosa.

    Flags comunes

    Estos flags están disponibles en cualquier *-cli de la suite (apps y primitivas de norma):

    Opción Descripción
    --json Emite el resultado como un único objeto JSON a stdout (envelope, ver abajo). Para consumo por agentes.
    --quiet Silencia banner y progreso; deja solo el resultado y los errores.
    --verbose Logging DEBUG a stderr.
    --schema Emite el contrato del CLI (flags, tipos, defaults, choices, exit codes) como JSON a stdout y termina.

    --quiet no silencia el resultado

    --quiet calla solo el ruido (banner, progreso, diagnóstico). El resultado se sigue imprimiendo. Para quedarte solo con el dato machine-readable, combina --json (que ya manda banner y progreso a stderr).

    Disciplina de streams

    La separación entre stdout y stderr es estricta y es lo que hace fiable el parseo:

    • stdout: SOLO el resultado. En modo humano, las líneas de resultado. En modo --json, un único objeto JSON.
    • stderr: todo lo demás — banner === <app> CLI ===, progreso, diagnóstico, logging y el aviso de auto-update.

    Capturar solo el resultado

    miapp-cli --edb modelo.edb --json 2>/dev/null

    Redirigir stderr a /dev/null deja en stdout exclusivamente el envelope JSON, listo para canalizar a jq u otro parser.

    El envelope --json

    Con --json, el CLI emite a stdout un único objeto. En caso de éxito:

    {
  "app": "miapp",
  "ok": true,
  "outputs": ["C:/proyectos/R4501/salida.xlsx"],
  "warnings": [],
  "summary": {}
}
    • app: nombre de la app (derivado del comando, sin el sufijo -cli/-batch).
    • ok: true si terminó bien.
    • outputs: rutas de los archivos generados (vacío si el CLI no escribe nada, p. ej. las primitivas de norma).
    • warnings: avisos no fatales.
    • summary: datos clave del resultado; su contenido depende de cada CLI.

    En caso de error:

    {
  "app": "miapp",
  "ok": false,
  "error": {
    "type": "InputError",
    "code": 3,
    "message": "no existe el .edb: C:/proyectos/falta.edb"
  }
}

    code coincide con el exit code (ver la tabla siguiente), de modo que un agente puede ramificar tanto por el código de salida del proceso como por el campo del envelope.

    Exit codes

    El exit code permite distinguir un fallo de input recuperable de un bug o de un problema de ETABS:

    Código Significado
    0 OK.
    1 Error inesperado (bug o excepción no clasificada).
    2 Uso o argumentos inválidos (lo emite argparse).
    3 Input faltante o ilegible (archivo que no existe, valor fuera de rango).
    4 ETABS no disponible o sin instancia activa cuando se requería.
    5 Fallo del pipeline de negocio (p. ej. modelo sin casos corridos).

    Cuáles aplican a cada CLI

    Los CLIs de las apps que abren ETABS pueden devolver 4; los que solo leen archivos pueden devolver 5. Las primitivas de norma (ds60-cli/nch433-cli/combinaciones-cli) no tocan ETABS ni archivos, así que en la práctica devuelven 0, 2 (argparse) o 3 (un valor inválido, p. ej. un R no tabulado). El envelope --schema lista los exit codes para cada CLI.

    Descubrimiento del contrato (--schema)

    --schema emite a stdout el contrato completo del CLI: flags, tipos, defaults, choices, required, posicionales, subcomandos y exit codes. El contrato se deriva por introspección del parser, así que refleja cualquier flag nuevo sin mantenimiento aparte y nunca queda desactualizado respecto al código.

    ds60-cli --schema

    {
  "app": "ds60",
  "prog": "ds60-cli",
  "description": "Confinamiento de elementos especiales de borde de muros (DS60 ...).",
  "schema_version": "1",
  "version": "0.1.0",
  "exit_codes": {
    "0": "OK",
    "1": "error inesperado (bug o excepcion no clasificada)",
    "2": "uso o argumentos invalidos (argparse)",
    "3": "input faltante o ilegible",
    "4": "ETABS no disponible o sin instancia activa",
    "5": "fallo del pipeline de negocio"
  },
  "arguments": [
    {"dest": "c", "help": "Profundidad del eje neutro [m].", "flags": ["--c"], "type": "float", "required": true}
  ]
}

    Por qué le sirve a un agente

    Un agente puede leer --schema una vez para conocer todas las opciones de un CLI (nombres exactos de flags, qué es requerido, qué valores admite cada choice, qué exit codes existen) sin parsear el --help ni leer esta documentación. Funciona aunque falten argumentos requeridos y sin tocar la red: el schema es descubrible sin configuración previa.

    CLIs con subcomandos

    Algunos CLIs agrupan su funcionalidad en subcomandos (p. ej. nch433-cli con factores y espectro-acel, o dxftoedb-cli con las etapas 1/2/3/4). En esos casos los flags comunes van ANTES del subcomando:

    nch433-cli --json factores --categoria II --zona 2 --suelo C ...

    --schema también describe los subcomandos de forma recursiva, así que un solo volcado expone el contrato completo.

    Auto-update

    Al arrancar, cualquier CLI consulta si hay una versión nueva de la suite y, de haberla, la instala silenciosamente. Bajo --json o --quiet ni siquiera se imprime el aviso, para no contaminar la salida. Se puede desactivar con la variable de entorno IEC_NO_AUTOUPDATE=1. Ver auto-update para el detalle.
